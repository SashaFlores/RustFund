## <a id='L-02'></a>L-02. Deadline Can Be Set Multiple Times            



## Summary

Contract logic doesn't properly enforce the “one-time” deadline setting rule via an explicit `deadline_set` flag, allow creators to repeatedly modify the campaign deadline.

## Vulnerability Details

The `set_deadline` function didn't update `deadline_set` member of `Fund` struct to true, which allow creators to change and/or modify deadline several times

```Rust
pub fn set_deadline(ctx: Context<FundSetDeadline>, deadline: u64) -> Result<()> {
        let fund = &mut ctx.accounts.fund;
        if fund.dealine_set {
            return Err(ErrorCode::DeadlineAlreadySet.into());
        }
        
        fund.deadline = deadline;
        Ok(())
    }
```

## Impact

* Business Logic Violation: Creators can bypass the "one-time deadline" rule, undermining contributor trust.
* Refund Evasion: Malicious creators can extend deadlines indefinitely to avoid refund conditions.
* Financial Risk: Contributors may lose funds if campaigns never meet goals but deadlines are repeatedly extended.
* Legal Risk: This vulnerability not only impacts user trust but also affects contract credibility, potentially leading to legal and reputational risks for the protocol.

## Recommendations

*Option One (Not Recommended/ less favorable):*

\
Update the `set_deadline` function to set `deadline_set = true` after setting the deadline to enforce immutability after the first successful call.

```Rust
pub fn set_deadline(ctx: Context<FundSetDeadline>, deadline: u64) -> Result<()> {
        let fund = &mut ctx.accounts.fund;
        if fund.deadline_set {
            return Err(ErrorCode::DeadlineAlreadySet.into());
        }
        
        fund.deadline = deadline;
        fund.deadline_set = true;         
        Ok(())
    }
```

*Option Two (Recommended):*

Set all funding details, including the deadline, at the time of fund creation `fund_create` function to eliminate the need for a separate deadline-setting function.


## Appeal Submitted

The initial report was classified as **low severity**, but I believe this finding should be **medium severity**, as the vulnerability involves **indirect impact on funds** and is easily exploitable by **anyone** due to the missing **access control** (which was not mentioned in the original report).

&#x20;

**Evaluation Based on Cyfrin Updraft Severity Guidelines:**

1. **Impact:**

   * The vulnerability **indirectly affects funds**:

     * The **lack of access control** allows **anyone**, not just the fund creator, to **shorten or extend the deadline**, manipulating the withdrawal process. This opens the possibility for premature withdrawals or delayed refunds.
     * Although funds are not immediately lost, this lack of control allows the **protocol’s core logic to be disrupted**, which can severely affect contributors' trust in the project and cause indirect financial harm to the protocol, thus **indirectly impacting funds**.
2. **Likelihood of Exploitation:**

   * The exploit is **easily triggered** by anyone with access, making it highly likely. Since the `deadline_set` flag is not being updated, it is straightforward for any user to **modify the deadline repeatedly** without any safeguards in place.
   * There are **no preconditions** needed, and **no additional logic or external conditions** are required to exploit this vulnerability, further supporting its **high likelihood**.

**Conclusion:** Based on Cyfrin’s classification, this issue meets the criteria for **medium severity** because:

* It has an **indirect impact on funds**.
* The exploit is **trivial and easily exploitable** by **anyone** (not just the creator) due to the **lack of access control**.
* The vulnerability doesn’t result in immediate direct financial loss, but it can lead to significant **protocol disruption**, which could indirectly affect funds and user trust.

**Final Severity: Medium**


## Judge Decision on Appeal: 
<span style="color:GREEN; font-weight:bold;">(Validated & updated to Medium Severity)</span>

I disagree with this: "..is easily exploitable by **anyone** due to the missing **access control**". The Anchor ensures that the fund has creator and that the creator is the caller:


```Rust
#[derive(Accounts)]
pub struct FundSetDeadline<'info> {
    #[account(mut,has_one = creator)]
    pub fund: Account<'info, Fund>,
    #[account(mut)]
    pub creator: Signer<'info>,
}
````
But I agree that there is indirect impact on the funds, because the creator can extend multiple times the deadline until the goal is reached. In that way the contributors lose their chance to refund their funds in case of unsuccessful campaign. Therefore I will accept the appeal and upgrade the severity of this issue to Medium.
